# 무명장야 · 사무전

기존 서버를 사용하는 정적 웹 게임입니다. `index.html`을 진입점으로 배포합니다.

## 파일 구성

| 파일 | 역할 |
| --- | --- |
| `index.html`, `game.css` | 화면 뼈대와 통합 스타일 |
| `game.js` | 기본 상태·게임 시계·공통 화면·초기화 |
| `config.js` | 운영 서버 설정 |

| `social.js` | 공용 교류 데이터 |
| `community.js` | 페어 게시판·텃밭·상점·푸시·중개소·PvP·저장 보호·로그 내보내기 |
| `visuals.js` | 도트 화면·생활 화면·밸런스 |
| `coop.js` | 공동 지갑·동행·공동 경매 |

| `assets/`, `sounds/` | 이미지와 효과음 |

| `tests/` | 파일 연결·페어 저장·브라우저·전투 모형 검증 |

각 통합 JS 안의 `module:` 주석은 원래 기능의 경계입니다. `index.html`의 스크립트 순서를 유지하고, `async`·`defer`·`type="module"`을 임의로 추가하지 마세요. 함수가 같은 전역 상태와 순차적인 확장을 사용합니다. 엄격 모드가 없던 설정·알림음·교류 코드는 별도 파일로 유지했습니다.

## 배포와 서버 설정

- 저장소 전체를 배포합니다. 이전의 `part*.js`와 개별 스타일 파일은 통합 파일로 대체되었습니다.
- `config.js`의 운영 서버 주소·공개 키를 유지합니다. 서버 비밀 키는 넣지 않습니다.
- 파일 정리와 클라이언트 수정은 기존 DB·계정·공동 지갑·채팅을 삭제하지 않습니다. 아래 서버 패치는 별도로 적용해야 합니다.
- 배포 뒤 페이지를 새로고침합니다. 통합 파일에는 새 캐시 버전이 지정되어 있습니다.
- 예전 안내·SQL·검증 결과는 저장소에서 정리했습니다. 신규 서버를 구축하거나 과거 설치 자료를 확인할 때에는 [정리 이전 버전](https://github.com/23342354/mumyeongjangya-game/tree/6bd6f4bc34557781092f4129675c5d600000aaf5)을 참고하세요. 초기화·전체 삭제 SQL을 운영 서버에 일괄 실행하지 마세요.

## 공동 동기화 서버 패치

의뢰 중 다른 활동이 막히거나 `57014 statement timeout`이 반복될 때에는, **`supabase/pair-sync-performance.sql`을 운영 Supabase의 SQL Editor에서 한 번 실행하고 이 PR의 사이트 파일도 배포해야 합니다.** 클라이언트만 교체하면 서버 잠금·반복 쓰기 개선은 적용되지 않습니다.

이 파일은 기존 `pair_play` 설치를 전제로 함수·인덱스·푸시 감시 트리거를 갱신합니다. 초기화 SQL이 아니며 계정·공동 지갑·채팅 행을 삭제하지 않습니다. 재실행할 수 있습니다. 과거 SQL을 모아서 실행하지 마세요.

배경 조회는 읽기 전용 `peek`를 사용합니다. 실제 소비·보상은 계속 CAS와 요청 영수증으로 직렬화합니다. 서버가 지연돼도 전체 화면이나 낚시 버튼을 잠그지 않으며, 수업·수행 클릭은 저장 대기열에 보관합니다. 채팅 목록과 커서는 공동 저장에서 분리하고, 타임아웃 뒤에는 일정 간격을 두고 재연결합니다.

## 서버 조회량 절감

Supabase가 `exceed_egress_quota`로 막히거나 `57014 statement timeout`이 반복되던 원인 중 하나는 클라이언트의 반복 조회였습니다. 교류 조회가 15초마다 게시글 2000개와 학생 목록 전체를 다시 받아 왔고, 보고 있는 화면이나 탭 상태와 무관하게 계속 돌았습니다.

- **숨은 탭에서는 조회를 멈춥니다.** `game.js`에 공통 조건 `pollAwake()`를 두고, 교류·페어 게시판·RP 알림·푸시 이력·중개소·대련·경매의 반복 조회가 이를 먼저 확인합니다. 다른 탭에 가 있거나 화면을 끈 동안에는 요청이 나가지 않고, 돌아온 직후 한 번에 따라잡습니다.
- **평소에는 새 글만 이어 받습니다.** 가진 마지막 글 번호 뒤의 글만 받아 목록 앞에 붙입니다. 전체 조회는 5분마다, 그리고 글을 쓰거나 지운 직후에만 실행합니다. 지운 글은 늦어도 5분 안에, 내가 지운 글은 즉시 사라집니다.
- **보는 화면에 따라 간격을 나눕니다.** 교류·명부·RP 게시판에서는 15초, 그 밖의 화면에서는 60초입니다. 게시판을 보고 있지 않아도 신청과 새 글 알림은 계속 도착합니다.

게시글 2000개·본문 평균 200자·학생 40명, 20명이 하루 중 게시판 2시간·다른 화면 2시간·탭 방치 6시간을 쓰는 기준으로 월 약 558GB에서 약 5.6GB로 줄어듭니다. 전체 게시판을 받는 횟수는 시간당 240회에서, 게시판을 보는 동안 12회·그 밖에는 0회가 됩니다.

추가 SQL은 필요하지 않습니다. 사이트 파일만 배포하고 새로고침하면 적용됩니다. 저장·계정·공동 지갑·거래 내역은 건드리지 않습니다.

## 용돈 기입장

광장 묶음에 **용돈 기입장** 화면이 생겼습니다. 륜이 어디서 들어오고 어디로 나갔는지 한 줄씩 쌓이며, 이름은 각자의 영혼 컬러(테마 색)로 표시합니다. 페어는 지갑을 함께 쓰므로 두 사람의 기록이 시각 순으로 한 목록에 섞여 보입니다.

- 상점·매점(여와 진열대 포함)·잡화점·강화·제작·농사·동아리·경매·거처·일세·장터·시험·탑·의뢰·중개소 등 륜이 움직이는 행동이 자동으로 기록됩니다. 따로 눌러야 하는 것은 없습니다.
- 수입은 `gainRin` 한 곳을, 지출은 공동 플레이 래퍼 한 곳을 지나가므로 행동마다 코드를 고칠 필요가 없습니다. 새 행동을 추가할 때 이름만 `LEDGER_LABELS`에 넣으면 한글 항목명이 붙고, 넣지 않아도 행동 이름 그대로 기록됩니다.
- 공동 플레이 행동 목록(`actions`)에 없으면서 륜을 건드리는 함수는 `LEDGER_EXTRA`에 이름을 넣어 기록만 더합니다. 공동 지갑을 다루는 방식은 바꾸지 않습니다. **새로 `S.rin`을 건드리는 코드를 넣을 때 두 목록 중 하나에 이름을 넣지 않으면 `npm test`가 잡아냅니다.**
- 같은 항목이 10분 안에 또 들어오면 한 줄로 합칩니다. 줄 수는 40줄까지 남기므로 저장본과 페어 전송량이 늘지 않습니다.

**파트너 기록을 함께 보려면 `supabase/ledger-peer.sql`을 Supabase SQL Editor에서 한 번 실행하세요.** 파트너 저장본에서 내려오는 항목 목록(`pp_peer`)에 `ledger` 한 줄을 더하는 것이 전부입니다. 표를 만들지도 지우지도 않고, 계정·공동 지갑·거래 내역을 건드리지 않으며, 여러 번 실행해도 결과가 같습니다. 실행하지 않아도 게임은 그대로 돌아가고, 기입장에 내 기록만 쌓입니다.

## 건의함 처리 (2026-11-04)

- **관문 통과 뒤 단계가 넘어가지 않던 문제** — 관문을 넘으면 열린 한도는 올라갔지만 고른 단계가 통과한 관문에 그대로 머물러, 진행이 막힌 것처럼 보였습니다. 이제 통과 직후 다음 단계를 골라 둡니다. 다음 관문이 무난하면 관문을, 아니면 안정적으로 갈 수 있는 가장 높은 단계를 집으며, **이미 깬 단계보다 아래로는 내려가지 않습니다.** 도중 귀환이 관문을 열지 않는 규칙은 그대로입니다.
- **내 정보에서 관계가 비어 보이던 문제** — 교류에서 맺은 관계는 서버에, 내 정보 화면이 읽는 `S.rel`은 기기에 따로 있어서 한쪽에만 보였습니다. 교류 기록을 받아올 때 `S.rel`도 함께 채웁니다. 내 정보에서 '끊기'를 눌러도 서버 기록이 지워집니다.
- **외출 보상이 들어오지 않던 문제** — 걸으며 모은 몫을 마지막에 "륜 +○○"로 **보여 주기만 하고 실제로 더하지 않았습니다.** 통행패만 쓰고 아무것도 받지 못하는 상태였습니다. 이제 걸음마다 바로 지급하므로, 도중에 창이 닫혀도 그때까지 번 몫은 남습니다.

## 효과가 겹치는 규칙

겹치는 것과 겹치지 않는 것이 섞여 있어 정리해 둡니다.

- **서로 다른 버프 아이템의 효과는 더해집니다.** 탕약 + 물약, 식사 + 디저트, 거기에 책·날씨·수행까지 같은 항목이면 전부 합산합니다. 예를 들어 연근산채 만두(경험치 +6%) · 달빛대추 만두(+13%) · 월병(+5%) · 맨드레이크 각성제(+25%)를 함께 두면 경험치 +49%가 됩니다.
- **같은 것을 또 쓰면 겹치지 않고 시간이 늘어납니다.** 같은 물약·같은 탕약은 남은 시간에 더해집니다(기본 지속시간의 최대 3배).
- **서로 다른 만두는 분류와 무관하게 최대 2종을 함께 적용합니다.** 식사 두 종류 또는 디저트 두 종류도 가능합니다. 세 번째 종류를 먹으려면 교체할 효과를 직접 고르며, 선택하거나 취소하기 전에는 소모하지 않습니다. 같은 만두는 효과 수치가 늘지 않고 지속시간만 기본의 최대 2배까지 연장합니다. 상한까지 1분 미만이면 소모하지 않아 빠른 연속 클릭이나 저장 응답 지연으로 낭비되지 않습니다.

현재 적용 중인 만두 2종은 상단 띠와 식당의 「만두 1 / 만두 2」에 표시됩니다. 각자 남은 시간 동안만 효과가 합산되며, 칩에 마우스를 올리면 효과를 확인할 수 있습니다. 식사/디저트는 만두 분류일 뿐 효과 칸을 제한하지 않습니다. 기존 `kit.eat`/`kit.dess` 두 저장 필드를 그대로 사용하므로 현재 효과와 페어 공유 처리는 보존되고 추가 SQL은 필요하지 않습니다.

## 도감은 합쳐서 맞춥니다

말랑이·영혼 인형 도감은 페어가 함께 쌓는 목록입니다. 예전에는 서버 기록이 내려올 때 목록을 통째로 덮어써서, 두 사람이 비슷한 때 새 항목을 얻으면 한쪽이 지워졌습니다. **인형을 산 화면에는 르셀리아가 떴는데 기록실에는 큰요우만 남는** 증상이 이것입니다.

- 서버 기록을 받을 때도, 내 변경을 다시 얹을 때도 도감 배열은 **합집합**으로 맞춥니다. 쌓이기만 하는 목록이라 합쳐도 잃는 것이 없습니다.
- 여와 진열대 구매(`yowaBuySpecial`)를 공동 지갑 거래 목록에 넣었습니다. 이제 다른 구매와 같이 한 번에 처리되고, 상대와 겹치면 기존 충돌 처리가 받아 줍니다.

이미 사라진 기록은 되살릴 수 없습니다. 앞으로 얻는 항목은 양쪽 모두 남습니다.

## 확인

Node.js로 `npm test`를 실행하면 JS 문법·HTML/CSS/에셋 참조·스크립트 순서·페어 저장 회귀·교류 조회량·용돈 기입장 검증을 수행합니다. 별도 설치 없이 실행할 수 있습니다.

`tests/ledger.cjs`는 기입장 기록을 확인합니다. 지출 금액과 항목 이름, 수입이 섞인 행동에서 지출만 가려내기, 같은 항목 합치기와 시간·부호에 따른 분리, 줄 수 상한, 행동이 중간에 실패해도 기록이 남는지를 검사하며 게임 전체나 서버 없이 돌아갑니다.

`tests/social-poll.cjs`는 모의 서버로 교류 조회를 확인합니다. 첫 전체 조회, 새 글만 이어받기, 중복 방지, 숨은 탭 정지와 복귀 추격, 화면별 간격, 삭제 반영, 2000개 상한, 과다 유입 시 전체 재조회를 검사하며 운영 서버로 요청하지 않습니다.

브라우저 검증은 `npm install`, `npx playwright install chromium` 뒤 `npm run test:browser`로 실행합니다. 테스트는 로컬 서버와 모의 응답을 사용하며 운영 서버로 요청하지 않습니다. 기존 버전과 비교하려면 `GAME_BASELINE_DIR=/path/to/old-version npm run test:browser`를 사용합니다. 준비된 Chromium을 쓸 경우 `CHROMIUM_EXECUTABLE`에 실행 파일 경로를 지정할 수 있습니다.

`npm run test:behavior`는 실제 브라우저에서 관문 진행·외출 보상·관계 연동과 효과 합산·표시를 확인합니다. 위 세 건이 되돌아가면 바로 실패합니다. 브라우저 검증과 같은 준비가 필요합니다.

선택적으로 `npm run test:combat`을 실행하면 Python 전투 모형의 진행 난도 증가 조건을 확인합니다.

`npm run test:sql`은 독립 PostgreSQL 엔진(PGlite)에서 SQL 재적용·읽기 전용 조회·중복 반영 방지·저장 횟수·선별 트리거를 확인합니다. `npm run test:pair-browser`는 같은 엔진을 모의 API로 연결한 Chromium에서 의뢰와 수업·수행·낚시의 병행, 지연 저장 중 채팅, 타임아웃 후 복구를 검증합니다. 두 테스트는 원래 설치 함수를 가져오기 위해 전체 Git 이력이 있는 체크아웃을 사용합니다.

## 페어 의뢰의 5분 갱신

페어 의뢰의 전투 진행·보상·일지는 5분마다 한 번에 반영하고, 전투별 문장 대신 처치·륜·경험치·지식·법구 수량을 요약합니다. 내부 전투 간격과 보상 공식은 그대로입니다. 남은 시간은 기기에서 계속 표시합니다. 수업·수행 완료 시각은 따로 확인하며, 해당 활동을 시작한다고 의뢰 전투를 추가 계산하지 않습니다. 의뢰 중 배경 공동 조회도 5분 간격으로 줄였습니다.

출발과 귀환은 바로 저장합니다. 5분 전에 귀환하면 아직 반영되지 않은 진행분을 먼저 계산하고 정산합니다. 남은 시간이 5분보다 짧으면 종료 시각에 처리합니다. 접속하지 않은 동안의 진행은 다음 갱신에서 합산합니다. 이 변경에 추가 SQL은 필요하지 않으며, 앞서 안내한 공동 동기화 서버 패치는 그대로 사용합니다.

## 낚시 입력과 어획 저장

페어 낚시의 던지기와 챔질은 서버 저장을 기다리지 않고 즉시 판정합니다. 성공한 클릭은 기기에 보관하고 어획 보상만 별도로 공동 저장합니다. 저장 대기 건수를 낚시 창에 표시하며, 같은 기기에서 새로고침한 뒤에도 다시 반영합니다. 확인된 어획은 다시 지급하지 않고, 늦게 도착한 보상 응답이 새로 던진 낚시를 초기화하지 않습니다.

던지기 간격 10초·하루 어획 보상 60회·실패/한도 이후 연습 규칙은 유지합니다. 서버 초기 연결 중에도 낚시 입력은 가능하며, 보상 반영은 연결 복구를 기다립니다. 이 수정에는 추가 SQL이 필요하지 않습니다.

## 중개소 조회와 저장 분리

중개소의 전체 매물·내 판매 기록·정산 대기 조회는 전체 게임 저장과 별도로 실행합니다. 조회는 계정·지갑을 쓰거나 현재 소지품을 덮어쓰지 않습니다. 실제 구매·등록·취소·정산은 기존 인증·공동 지갑·중복 처리 방지를 유지합니다. 서버가 거래 완료를 확인했으나 잔액 갱신만 늦어지면 거래 완료와 갱신 대기를 구분해 표시합니다.

이 기능을 적용할 때에는 **최신 `supabase/pair-sync-performance.sql` 전체를 Supabase SQL Editor에서 한 번 다시 실행하고 사이트 파일을 배포**하세요. 기존 파일에 읽기 전용 `market_read`를 추가하고 구 조회 주소도 읽기 전용으로 연결했습니다. 별도 SQL 파일을 만들지 않았으며 재실행해도 거래 내역·계정·공동 지갑을 초기화하지 않습니다.

### 직접 만드는 4인 모임

`supabase/clubs.sql` 전체를 운영 Supabase SQL Editor에서 한 번 실행한 뒤 최신 사이트 파일을 배포합니다. 기존 계정·공동 지갑·공용 채팅은 변경하지 않습니다. 설치 SQL은 재실행할 수 있습니다. 설치 전에는 모임 화면에 연결 안내가 표시됩니다.

교류 → 모임에서 이름(2~20자)과 소개(200자까지)를 입력해 무료로 개설하거나 공개 목록에서 가입합니다. **모임장 포함 최대 4명, 한 계정당 한 모임**이며 정원은 서버에서 검사합니다. 정해진 세 곳에 가입하던 이전 개인 모임 대신 실제 부원들이 함께 성장하는 모임을 사용합니다. 이전 개인 모임 저장값은 삭제하지 않지만 그 혜택은 새 모임 혜택으로 대체됩니다.

한국 시간 자정 기준 부원마다 하루 한 번 출석할 수 있고, 출석마다 모임 누적 경험치가 10 오릅니다. 100 경험치마다 한 레벨, 최대 Lv 10입니다. 혜택은 부원에게 자동 적용되며 중복 출석이나 재전송으로 경험치가 늘지 않습니다.

| 레벨 | 해금 혜택 |
| --- | --- |
| 1 | 지식 +2% |
| 3 | 전리품 +3% |
| 5 | 륜 획득 +3% |
| 7 | 수업 보상 +5% |
| 10 | 지식 추가 +3%, 전리품 추가 +2% (합계 각각 +5%) |

모임 채팅은 RP/오너 모드를 지원하고 서버에서 현재 회원을 확인합니다. 공용 messages 테이블과 분리되어 비회원·탈퇴자에게 기록을 반환하지 않습니다. 읽고 있는 모임 채팅은 5초 간격으로 새 글만 조회하며, 숨은 탭은 조회를 멈춥니다. 모임 목록은 모임 화면에서만 받습니다. 전송 실패 시 초안을 유지하고 같은 내용 재시도는 요청 ID로 중복을 방지합니다.

모임장이 탈퇴하면 가장 먼저 가입한 남은 부원에게 자동 승계합니다. 마지막 부원이 나가면 해당 모임과 해당 모임 채팅만 삭제됩니다. 회원 목록·경험치는 개인 저장본과 별도로 관리하므로 페어 저장 대기를 기다리지 않습니다.

검증: `npm run test:clubs`(PostgreSQL 기능·권한·4명 정원), `npm run test:clubs-browser`(실제 화면·서버 연결·비공개 채팅·재전송·레벨 혜택). 기존 `npm test`에도 모임 SQL 검증을 포함합니다.

### 4인 모임 확장 업데이트

**기존 모임을 설치했어도 최신 `supabase/clubs.sql` 전체를 SQL Editor에서 한 번 다시 실행한 뒤 사이트를 배포합니다.** 기존 모임·부원·출석·채팅은 보존합니다. 이 확장은 운영 중인 계정·중개소·페어 공동 지갑 함수(`pp_wallet`, `pp_apply` 등)를 사용합니다. 과거 설치 SQL을 다시 실행할 필요는 없습니다.

정원은 **모임장 포함 4명**입니다. 모임 화면은 정보·기여 / 부원 / 모임방 / 게시판 / 공용 창고 / 기록 / 다른 모임의 일곱 탭으로 나눴습니다.

- 정보·기여: 공지·소개·가입 방식 편집, 출석, 륜 기부. 기부는 하루 200점까지이며 1점당 474륜이 공용 금고로 이동하고 모임 경험치·개인 기여도를 같은 점수만큼 올립니다.
- 부원: 이름·레벨·출석·기여도·가입일, 가입 신청 승인/거절, 창고 출납 권한 부여/회수, 모임장 위임·부원 내보내기. 가입 방식은 자유 가입 / 승인제 / 모집 중지입니다.
- 모임방: 네 사람의 자리와 출석 표시, 등불·서고·달빛 분위기, 모임장 메모. 금고의 륜으로 최대 5단계까지 확장하며 창고가 60칸에서 단계당 10칸씩 늘어납니다. 다음 단계 비용은 현재 단계 × 10,000륜입니다.
- 게시판: 부원만 읽는 게시글·댓글, 본인 또는 모임장의 삭제. 최근 글·댓글 150개를 표시합니다.
- 공용 창고: 륜 금고, 재료·각인 재료·건축/개별 재료·물약·씨앗·요리·법구 넣기/꺼내기. 누구나 입고할 수 있고 출고는 모임장과 출납 권한을 받은 부원만 가능합니다. 물품은 한 번에 99개까지, 씨앗은 부원당 하루 10개까지 인출할 수 있습니다. 같은 종류는 수량이 합쳐지고 법구는 한 개당 한 칸을 차지합니다. 귀속·잠금·착용 법구는 넣을 수 없으며, 인출 법구에는 수령 지갑의 새 아이템 ID가 부여됩니다.
- 기록: 서버에서 남긴 최근 100건의 부원 활동·권한 변경·게시판·금고/창고 출납을 필터로 확인합니다.
- 다른 모임: 이름·소개 검색, 레벨/부원 레벨 합/인원/생성일 정렬, 공개 소개 살펴보기, 가입 신청·취소. 다른 모임의 금고·게시판·기록은 공개하지 않습니다.

출납은 서버 트랜잭션에서 지갑과 모임 창고를 함께 변경합니다. 페어 부원이 넣거나 꺼내면 공동 지갑에 반영되고, 페어 저장 revision도 함께 올라 이전 저장본으로 복원되지 않습니다. 요청 ID 영수증을 별도 보관하므로 응답 유실 후 재시도해도 두 번 옮기지 않습니다. 개인 지갑에서는 출납 중 발생한 수입을 보존하고 사용자의 다른 자원 변경 동작은 출납 확인 뒤 실행합니다. 마지막 부원은 금고와 창고를 비운 뒤 탈퇴해야 합니다.

기존 레벨 혜택과 부원 전용 모임 채팅은 유지됩니다. 데이터 조회는 읽기 전용이며 모임 상세 화면을 보고 있을 때만 창고·게시판·기록·목록을 가져옵니다.

### 떠돌이 상인 레벨대별 진열

기존 공용 경매가 설치된 서버에서 **`supabase/merchant-levels.sql` 전체를 Supabase SQL Editor에서 한 번 실행**하고 최신 사이트 파일을 배포합니다. 기존 경매표에 레벨대 구분을 추가하며, 이미 입찰된 법구·보증금·낙찰품은 변경하지 않습니다. 이전 품목은 해당 회차가 끝날 때까지 「기존 경매」로 함께 표시됩니다. SQL은 재실행할 수 있습니다.

기본 진열은 내 현재 레벨대입니다. 10레벨대는 Lv 10~19, 20레벨대는 Lv 20~29처럼 나누고, Lv 1~9는 별도 입문 구간으로 둡니다. 화면의 「진열 레벨대」에서 다른 구간을 선택하거나 「내 레벨대 보기」로 돌아올 수 있습니다. 목록은 최소 100레벨대까지, 이후에는 내 레벨대보다 두 구간 위까지 표시합니다.

각 구간에 **희귀·영웅·전설 한 점씩** 생성합니다. 법구 레벨·기본 능력치·시작가는 구간에 맞춰 달라지며, 같은 구간을 보는 러너들은 동일한 서버 경매품에 입찰합니다. 품질은 무작위로 바뀌지 않고 옵션 수도 각각 2/3/4개입니다. 요청한 구간만 생성하므로 조회하지 않은 구간 전체를 매번 만들지 않습니다. 내 레벨이 달라져도 이미 입찰한 물건의 레벨과 품질은 그대로 유지됩니다.

매시 00~15분 경매, 입찰 경쟁·자동 환불·귀속·낙찰품 수령은 기존 규칙을 유지합니다. 낙찰품 수령 목록과 최근 결과에는 레벨대와 품질도 함께 표시합니다.

검증: `npm run test:merchant`(마이그레이션 재실행·레벨 구간·고정 품질·기존 입찰 보존·중복 차감/수령 방지), `npm run test:merchant-browser`(실제 구간 전환·입찰·모바일 화면). 테스트는 기존 설치 함수를 읽기 위해 전체 Git 이력이 필요합니다.

### 연무제 인물 말투와 제2회 대진

연무제 대진과 대사는 `gameplay.js`의 `ARENA_ROSTERS`에서 회차별로 관리합니다. 제공된 NPC 설정에 맞춰 삼장의 차분한 존댓말, 강시의 짧은 반말, 양귀비의 느긋하고 세심한 교사 말투, 항아의 장난기와 전투 판단, 여와의 조심스럽고 전문적인 설명, 염라의 관대한 어른 말투를 반영했습니다. 각 인물에게 등장·플레이어 승리·플레이어 패배 대사를 따로 두었습니다. 양귀비를 독심/거짓 판별 능력자로 표현하지 않으며, 비전투원인 여와는 본인이 직접 싸우는 대신 제작한 시험 장치의 담당자로 등장합니다.

1회는 기존 15회전 진행을 유지하고, 완주 즉시 별도의 2회 대진 15개가 열립니다. 2회는 강화형 의체 괴한·밀매상 조직 간부·상위 사역물·강화 업귀에서 시작해 강시의 정문 수비, 삼장의 석장 대련, 여와의 고출력 시험 장치, 양귀비의 공명 교정, 항아의 가속 교련, 강시·양귀비 합동 평가, 항아·삼장 페어 교련을 거쳐 염라의 최종 평가로 이어집니다. 합동 평가와 상위 개체 표기는 연무제용 교련 편성이며 신규 고유 NPC의 공식 설정을 추가하지 않습니다.

2회 첫 상대부터 1회 결승보다 체력·초당 피해가 모두 높습니다. 1회 난도와 기존 페어 배율은 유지하고, 2회부터는 회전과 회차가 진행될 때 난도가 내려가지 않도록 조정했습니다. 3회 이후에는 심화 대진을 재사용하며 수치가 계속 올라갑니다. 기존 회차·회전·최고 기록을 초기화하지 않습니다.

교직원 대련의 문구는 「처치」 대신 「제압」으로 정리했습니다. 완주 보상은 기존 규칙을 유지하며 마지막 회전의 기여도도 누락되지 않습니다. 별도 SQL은 필요 없습니다. 검증은 `npm run test:arena`와 실제 PostgreSQL을 연결한 `npm run test:pair-browser`로 수행합니다.
