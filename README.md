# 무명장야 · 사무전

기존 서버를 사용하는 정적 웹 게임입니다. `index.html`을 진입점으로 배포합니다.

## 파일 구성

| 파일 | 역할 |
| --- | --- |
| `index.html`, `game.css` | 화면 뼈대와 통합 스타일 |
| `game.js` | 기본 상태·게임 시계·공통 화면·초기화 |
| `config.js` | 운영 서버 설정 |
| `notifications.js` | 알림음 |
| `gameplay.js` | 전투·성장·거처·제작·계정 |
| `social.js` | 공용 교류 데이터 |
| `community.js` | 페어 게시판·텃밭·상점·푸시·중개소·PvP·저장 보호·로그 내보내기 |
| `visuals.js` | 도트 화면·생활 화면·밸런스 |
| `coop.js` | 공동 지갑·동행·공동 경매 |
| `notification-worker.js` | 웹 푸시 서비스 워커 |
| `assets/`, `sounds/` | 이미지와 효과음 |
| `supabase/functions/` | 푸시 서버 함수 |
| `scripts/` | VAPID 키 생성·건의함 Apps Script |
| `tests/` | 파일 연결·페어 저장·브라우저·전투 모형 검증 |

각 통합 JS 안의 `module:` 주석은 원래 기능의 경계입니다. `index.html`의 스크립트 순서를 유지하고, `async`·`defer`·`type="module"`을 임의로 추가하지 마세요. 함수가 같은 전역 상태와 순차적인 확장을 사용합니다. 엄격 모드가 없던 설정·알림음·교류 코드는 별도 파일로 유지했습니다.

## 배포와 서버 설정

- 저장소 전체를 배포합니다. 이전의 `part*.js`와 개별 스타일 파일은 통합 파일로 대체되었습니다.
- `config.js`의 운영 서버 주소·공개 키를 유지합니다. 서버 비밀 키는 넣지 않습니다.
- 파일 정리와 클라이언트 수정은 기존 DB·계정·공동 지갑·채팅을 삭제하지 않습니다. 아래 서버 패치는 별도로 적용해야 합니다.
- 배포 뒤 페이지를 새로고침합니다. 통합 파일에는 새 캐시 버전이 지정되어 있습니다.
- 예전 안내·SQL·검증 결과는 저장소에서 정리했습니다. 신규 서버를 구축하거나 과거 설치 자료를 확인할 때에는 [정리 이전 버전](https://github.com/23342354/mumyeongjangya-game/tree/6bd6f4bc34557781092f4129675c5d600000aaf5)을 참고하세요. 초기화·전체 삭제 SQL을 운영 서버에 일괄 실행하지 마세요.

## 공동 동기화 서버 패치

의뢰 중 다른 활동이 막히거나 `57014 statement timeout`이 반복될 때에는, **`supabase/pair-sync-performance.sql`을 운영 Supabase의 SQL Editor에서 한 번 실행하고 이 PR의 사이트 파일도 배포해야 합니다.** 클라이언트만 교체하면 서버 잠금·반복 쓰기 개선은 적용되지 않습니다.

이 파일은 기존 `pair_play` 설치를 전제로 함수·인덱스·푸시 감시 트리거를 갱신합니다. 초기화 SQL이 아니며 계정·공동 지갑·채팅 행을 삭제하지 않습니다. 재실행할 수 있습니다. 과거 SQL을 모아서 실행하지 마세요.

배경 조회는 읽기 전용 `peek`를 사용합니다. 실제 소비·보상은 계속 CAS와 요청 영수증으로 직렬화합니다. 서버가 지연돼도 전체 화면이나 낚시 버튼을 잠그지 않으며, 수업·수행 클릭은 저장 대기열에 보관합니다. 채팅 목록과 커서는 공동 저장에서 분리하고, 타임아웃 뒤에는 일정 간격을 두고 재연결합니다.

## 서버 조회량 절감

Supabase가 `exceed_egress_quota`로 막히거나 `57014 statement timeout`이 반복되던 원인 중 하나는 클라이언트의 반복 조회였습니다. 교류 조회가 15초마다 게시글 2000개와 학생 목록 전체를 다시 받아 왔고, 보고 있는 화면이나 탭 상태와 무관하게 계속 돌았습니다.

- **숨은 탭에서는 조회를 멈춥니다.** `game.js`에 공통 조건 `pollAwake()`를 두고, 교류·페어 게시판·RP 알림·푸시 이력·중개소·대련·경매의 반복 조회가 이를 먼저 확인합니다. 다른 탭에 가 있거나 화면을 끈 동안에는 요청이 나가지 않고, 돌아온 직후 한 번에 따라잡습니다.
- **평소에는 새 글만 이어 받습니다.** 가진 마지막 글 번호 뒤의 글만 받아 목록 앞에 붙입니다. 전체 조회는 5분마다, 그리고 글을 쓰거나 지운 직후에만 실행합니다. 지운 글은 늦어도 5분 안에, 내가 지운 글은 즉시 사라집니다.
- **보는 화면에 따라 간격을 나눕니다.** 교류·명부·RP 게시판에서는 15초, 그 밖의 화면에서는 60초입니다. 게시판을 보고 있지 않아도 신청과 새 글 알림은 계속 도착합니다.

게시글 2000개·본문 평균 200자·학생 40명, 20명이 하루 중 게시판 2시간·다른 화면 2시간·탭 방치 6시간을 쓰는 기준으로 월 약 558GB에서 약 5.6GB로 줄어듭니다. 전체 게시판을 받는 횟수는 시간당 240회에서, 게시판을 보는 동안 12회·그 밖에는 0회가 됩니다.

추가 SQL은 필요하지 않습니다. 사이트 파일만 배포하고 새로고침하면 적용됩니다. 저장·계정·공동 지갑·거래 내역은 건드리지 않습니다.

## 용돈 기입장

광장 묶음에 **용돈 기입장** 화면이 생겼습니다. 륜이 어디서 들어오고 어디로 나갔는지 한 줄씩 쌓이며, 이름은 각자의 영혼 컬러(테마 색)로 표시합니다. 페어는 지갑을 함께 쓰므로 두 사람의 기록이 시각 순으로 한 목록에 섞여 보입니다.

- 상점·잡화점·강화·제작·농사·동아리·경매·거처·시험·탑·의뢰 등 륜이 움직이는 행동이 자동으로 기록됩니다. 따로 눌러야 하는 것은 없습니다.
- 수입은 `gainRin` 한 곳을, 지출은 공동 플레이 래퍼 한 곳을 지나가므로 행동마다 코드를 고칠 필요가 없습니다. 새 행동을 추가할 때 이름만 `LEDGER_LABELS`에 넣으면 한글 항목명이 붙고, 넣지 않아도 행동 이름 그대로 기록됩니다.
- 같은 항목이 10분 안에 또 들어오면 한 줄로 합칩니다. 줄 수는 40줄까지 남기므로 저장본과 페어 전송량이 늘지 않습니다.

**파트너 기록을 함께 보려면 `supabase/ledger-peer.sql`을 Supabase SQL Editor에서 한 번 실행하세요.** 파트너 저장본에서 내려오는 항목 목록(`pp_peer`)에 `ledger` 한 줄을 더하는 것이 전부입니다. 표를 만들지도 지우지도 않고, 계정·공동 지갑·거래 내역을 건드리지 않으며, 여러 번 실행해도 결과가 같습니다. 실행하지 않아도 게임은 그대로 돌아가고, 기입장에 내 기록만 쌓입니다.

## 확인

Node.js로 `npm test`를 실행하면 JS 문법·HTML/CSS/에셋 참조·스크립트 순서·페어 저장 회귀·교류 조회량·용돈 기입장 검증을 수행합니다. 별도 설치 없이 실행할 수 있습니다.

`tests/ledger.cjs`는 기입장 기록을 확인합니다. 지출 금액과 항목 이름, 수입이 섞인 행동에서 지출만 가려내기, 같은 항목 합치기와 시간·부호에 따른 분리, 줄 수 상한, 행동이 중간에 실패해도 기록이 남는지를 검사하며 게임 전체나 서버 없이 돌아갑니다.

`tests/social-poll.cjs`는 모의 서버로 교류 조회를 확인합니다. 첫 전체 조회, 새 글만 이어받기, 중복 방지, 숨은 탭 정지와 복귀 추격, 화면별 간격, 삭제 반영, 2000개 상한, 과다 유입 시 전체 재조회를 검사하며 운영 서버로 요청하지 않습니다.

브라우저 검증은 `npm install`, `npx playwright install chromium` 뒤 `npm run test:browser`로 실행합니다. 테스트는 로컬 서버와 모의 응답을 사용하며 운영 서버로 요청하지 않습니다. 기존 버전과 비교하려면 `GAME_BASELINE_DIR=/path/to/old-version npm run test:browser`를 사용합니다. 준비된 Chromium을 쓸 경우 `CHROMIUM_EXECUTABLE`에 실행 파일 경로를 지정할 수 있습니다.

선택적으로 `npm run test:combat`을 실행하면 Python 전투 모형의 진행 난도 증가 조건을 확인합니다.

`npm run test:sql`은 독립 PostgreSQL 엔진(PGlite)에서 SQL 재적용·읽기 전용 조회·중복 반영 방지·저장 횟수·선별 트리거를 확인합니다. `npm run test:pair-browser`는 같은 엔진을 모의 API로 연결한 Chromium에서 의뢰와 수업·수행·낚시의 병행, 지연 저장 중 채팅, 타임아웃 후 복구를 검증합니다. 두 테스트는 원래 설치 함수를 가져오기 위해 전체 Git 이력이 있는 체크아웃을 사용합니다.

## 페어 의뢰의 5분 갱신

페어 의뢰의 전투 진행·보상·일지는 5분마다 한 번에 반영하고, 전투별 문장 대신 처치·륜·경험치·지식·법구 수량을 요약합니다. 내부 전투 간격과 보상 공식은 그대로입니다. 남은 시간은 기기에서 계속 표시합니다. 수업·수행 완료 시각은 따로 확인하며, 해당 활동을 시작한다고 의뢰 전투를 추가 계산하지 않습니다. 의뢰 중 배경 공동 조회도 5분 간격으로 줄였습니다.

출발과 귀환은 바로 저장합니다. 5분 전에 귀환하면 아직 반영되지 않은 진행분을 먼저 계산하고 정산합니다. 남은 시간이 5분보다 짧으면 종료 시각에 처리합니다. 접속하지 않은 동안의 진행은 다음 갱신에서 합산합니다. 이 변경에 추가 SQL은 필요하지 않으며, 앞서 안내한 공동 동기화 서버 패치는 그대로 사용합니다.

## 낚시 입력과 어획 저장

페어 낚시의 던지기와 챔질은 서버 저장을 기다리지 않고 즉시 판정합니다. 성공한 클릭은 기기에 보관하고 어획 보상만 별도로 공동 저장합니다. 저장 대기 건수를 낚시 창에 표시하며, 같은 기기에서 새로고침한 뒤에도 다시 반영합니다. 확인된 어획은 다시 지급하지 않고, 늦게 도착한 보상 응답이 새로 던진 낚시를 초기화하지 않습니다.

던지기 간격 10초·하루 어획 보상 60회·실패/한도 이후 연습 규칙은 유지합니다. 서버 초기 연결 중에도 낚시 입력은 가능하며, 보상 반영은 연결 복구를 기다립니다. 이 수정에는 추가 SQL이 필요하지 않습니다.

## 중개소 조회와 저장 분리

중개소의 전체 매물·내 판매 기록·정산 대기 조회는 전체 게임 저장과 별도로 실행합니다. 조회는 계정·지갑을 쓰거나 현재 소지품을 덮어쓰지 않습니다. 실제 구매·등록·취소·정산은 기존 인증·공동 지갑·중복 처리 방지를 유지합니다. 서버가 거래 완료를 확인했으나 잔액 갱신만 늦어지면 거래 완료와 갱신 대기를 구분해 표시합니다.

이 기능을 적용할 때에는 **최신 `supabase/pair-sync-performance.sql` 전체를 Supabase SQL Editor에서 한 번 다시 실행하고 사이트 파일을 배포**하세요. 기존 파일에 읽기 전용 `market_read`를 추가하고 구 조회 주소도 읽기 전용으로 연결했습니다. 별도 SQL 파일을 만들지 않았으며 재실행해도 거래 내역·계정·공동 지갑을 초기화하지 않습니다.
